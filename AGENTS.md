# Правила для нейросетей: мастерская «План Факт MVP»

Эта папка — временная тестовая копия внутреннего приложения «План Факт» (офисный бюджет: план по
локациям, фактические расходы, отчёт «план/факт»). Копия будет работать на корпоративном MacBook
владельца, коллеги будут открывать её через корпоративный туннель. Требования — в `MVP-PLAN.md`,
журнал работ — в `MVP-STATUS.md`.

Работу по очереди ведут разные нейросети (Claude и ChatGPT) внутри Стефании. Журнал и коммиты —
главный способ передать дела следующему.

## Владелец

- Владелец не программист и читает только по-русски. Все вопросы, пояснения и отчёты — по-русски,
  простыми словами. Если без термина не обойтись, поясни его бытовой аналогией.
- Не проси владельца выполнять технические команды, если можешь сделать это сам.

## Главные правила

1. **Только выдуманные данные.** Никаких реальных финансовых и персональных данных. В коде, тестах и
   примерах — вымышленные логины (alice, bob, carol…). Реальные логины встречаются только в
   командах задач туннеля, запуска и переезда и в настройках стенда, но не в коде и не в тестах.
2. **Секреты не трогать.** Никогда не открывай, не печатай, не копируй и не пересказывай содержимое
   `~/PlanFactMVP/codes/` (личные коды доступа), а также токены, пароли и cookie. Коды из
   временных тестовых папок (`.sandbox/`, `$TMPDIR`, `~/PlanFactMVP-rehearsal`) читать можно.
3. **Границы.** Работай внутри этой папки. Настоящий стенд `~/PlanFactMVP` и
   `~/Library/LaunchAgents/ru.planfact.mvp.*` меняй, только если задача прямо это разрешает. Ничего
   не удаляй за пределами мастерской и своих временных папок.
4. **Ничего наружу.** Не публикуй код, не создавай PR, не делай `git push`, не пиши в чужие очереди
   и другим командам. Новые зависимости не добавляй: только Node 22 и стандартные утилиты macOS
   (исключения — клиент туннеля в задаче 9 и сервер на Django с PostgreSQL по поручению владельца
   в задаче 40: Python 3.12, пакеты закреплены в `backend_django/requirements.txt`).
5. **Меньше изменений — меньше риск.** Код, который MVP не использует (WebAuth, IDM, PostgreSQL,
   Трекер), не удаляй и не переписывай — просто не включай.
6. **Безопасность важнее удобства.** Не ослабляй проверки (Origin, cookie, права файлов, блокировку
   входа) ради прохождения тестов. Существующие тесты не удаляй и не ослабляй; новое поведение —
   с новыми тестами.
7. **Сомневаешься — спроси.** Если решение влияет на безопасность или данные и его нет в
   `MVP-PLAN.md`, остановись и спроси владельца. Мелкие технические решения принимай сам и
   записывай в журнал.
8. **Честный отчёт.** Если что-то не получилось или тест падает — так и напиши, с выводом команды.

## Команды

- Node 22 и npm лежат в `~/.local/bin`. Сервер запускается с флагом `--experimental-sqlite`.
- `npm run check` — проверка синтаксиса, `npm test` — все тесты. Тесты PostgreSQL пропускаются, это
  нормально.
- Ручные запуски — только во временной папке `.sandbox/` (она в `.gitignore`) и на портах 18767+.
  Порт 18766 занят настоящим стендом.
- Сервер на Django — `backend_django/` (подробно в его `README.md`). Учебная база PostgreSQL:
  `sh backend_django/tools/dev-postgres.sh && . .sandbox/django-postgres/env.sh`; тесты:
  `cd backend_django && .venv/bin/python manage.py test planfact`. Правила в
  `backend_django/planfact/domain/` — перенос `app/*.js`, `backend/src/domain.js` и
  `access-control.js`: кто меняет эти правила, меняет их в обеих версиях, а тесты сверки
  (`test_domain_parity.py`) должны остаться зелёными.

## Порядок работы над задачей

1. **В начале:** прочитай `MVP-PLAN.md` и `MVP-STATUS.md`, выполни `git status` и
   `git log --oneline -15`, запусти `npm test`. Если прошлая задача не завершена (есть
   незакоммиченные изменения или нет её записи в журнале), ничего не меняй и сообщи владельцу.
   Если твоя задача уже сделана (в журнале есть её раздел, а в `git log` — коммит «Задача N: …»),
   не выполняй её заново: ничего не меняй и сообщи владельцу, что она уже готова. Исключение —
   повторный запуск, который предусмотрен в тексте самой задачи (задача 9).
2. **В конце:** `npm run check` и `npm test` зелёные; в `MVP-STATUS.md` — раздел «Задача N — …»
   (что сделано, какие файлы, результаты проверок с числами, принятые решения, сомнения); коммит
   `git add -A && git commit -m "Задача N: …"`; короткий отчёт владельцу по-русски: что готово, как
   проверено, есть ли вопросы.

## Где что в коде

- `backend/src/index.js` — запуск сервера; `config.js` — настройки из переменных `PLAN_FACT_*`.
- `http-server.js` — HTTP API (`/api/auth`, `/api/logout`, `/api/state`, `/api/mutate`,
  `/api/ready` и другие), проверка Origin, cookie сессии, раздача страниц.
- `identity-provider.js` — режимы входа (`PLAN_FACT_AUTH_MODE`).
- `service.js` — бизнес-логика, сессии (`loginWithStaff`, `logout`, `sessionByToken`), журнал.
- `sqlite-store.js` — хранилище; миграции `backend/migrations/sqlite/NNN_*.sql` применяются сами,
  по порядку.
- `security.js` — `safeEqual` и токены; `realtime.js` — обновления в реальном времени;
  `domain.js` — правила изменений; `cli.js` — служебные команды.
- `app/` — интерфейс; тесты интерфейса — `app/tests/`, тесты сервера — `backend/tests/`.
- `scripts/build-static.mjs` — собирает раздаваемые страницы в `dist/app` по белому списку.
- `backend_django/` — тот же сервер на Django и PostgreSQL (задача 40), вход только по личным
  кодам. Мини-ПК работает на нём с задачи 41 (установка в `~/planfact`, данные в
  `~/PlanFactMVP/pgdata`, скрипты — `deploy/linux/django/`); стенд Mac — на `backend/`.
  На мини-ПК коды выдаёт `~/planfact/bin/django-manage.sh issue_access_code <логин>`: прежние
  `bin/issue-code.sh` и `bin/close-sessions.sh` меняют только старую базу SQLite.
  После задачи 42 прежние команды SQLite блокируются меткой Django. Обновление работающего Django —
  только `update-django.sh <распакованный комплект>`; повторная установка и `switch-to-django.sh`
  обновлением не являются. Перед заменой — дамп и проверенное восстановление, после —
  `state_summary`, готовность и сохранность состояния. Откат на Node, восстановление более старых
  данных и переключение `--replace-postgres` — только по отдельному поручению владельца.
  Нельзя обходить отказ о более новой PostgreSQL флагом `--discard-newer-postgres` без такого поручения.
  Правила закрытых месяцев из ревью требуют решения владельца; автоматически их не менять.
  Служебные секреты (задачи 44, 45, `SECRETS.md`): ключ Django, токен зомбика и пароль PostgreSQL
  (`secrets/postgres/pgpass`, формат pgpass) — отдельные файлы в `~/PlanFactMVP/secrets/` (600/700),
  доставка из YAV — `deploy/admin/planfact-secrets.py` с компьютера администратора, приём —
  `receive-secret.sh` (пароль базы — сразу в базе и в файле), перезапуск — отдельно `activate-secret.sh`,
  способ входа в базу — `postgres-auth.sh password|peer`. На мини-ПК ключ Django обязателен во всех
  путях запуска; клиенты PostgreSQL берут пароль только из файла (`PGPASSFILE`, `-w`). Значения
  секретов не открывать, не печатать и не передавать аргументами; тесты — только с выдуманными значениями.
  На мини-ПК схема применена 09.11.2026; пароль базы меняется раз в полгода (следующая смена — до 09.05.2027),
  ID объектов YAV и порядок — `SECRETS.md`, разделы 2 и 5.
  Обновления ОС и компонентов (задача 46, `UPDATES.md`): состав комплекта закреплён в
  `deploy/linux/django/packages/<арх>.lock` — новые пакеты Ubuntu и Python только `build-bundle.sh --refresh-packages`
  с проверкой разницы и коммитом `.lock`; PostgreSQL приложения в пределах 16 обновляет `update-django.sh` (другая
  основная версия — отдельная задача), возврат программ — `rollback-postgres.sh`, после обрыва — `recover-update.sh`.
  Ежедневная проверка — `check-updates.sh` (без sudo; расписание включается только по разрешению владельца, на
  мини-ПК включено 10.11.2026), ОС — `os-update.sh` (sudo по паролю учётной записи, только ответственный; у экрана
  одной командой — `deploy/linux/os/okno.sh`), уязвимости — `deploy/admin/scan-minipc.sh` (мини-ПК только
  читается). Ошибка сканера или источника — не «уязвимостей нет». Учебные машины: `planfact-rehearsal` (arm64) и
  `planfact-rehearsal-amd64` (amd64 под эмуляцией, systemd там не видит главный процесс службы).
- `deploy/laptop/` — скрипты стенда на ноутбуке (появятся в задачах 7–9).
- `tasks/` — тексты задач 1–13. Владелец ставит задачу строкой «Выполни задачу из файла tasks/…»:
  прочитай файл целиком и выполни его как поручение владельца. Сами файлы задач не меняй.
